## Private signing (interface only, disabled by default)

`private_signature` implements deterministic, domain-separated `atto-private-guest-attestation-v1` signing-statement bytes binding exact repository, commit/tree, fixture hash, GitHub run/attempt/job, artifact SHA-256, verifier-issued challenge nonce, approved signer workflow, claimed runner identity, backend and feature. It offers `PrivateSigningService` for future independently-administered KMS/HSM integration, but **SigningDisabled** is the only production signer supplied. The Rust verifier can check a 64-byte Ed25519 detached signature using OpenSSL against **exact pinned PEM SHA-256**, explicit key validity dates and revocation. No keys, cloud secrets, signing API access or public transparency-log uploads are created. Rust tests generate ephemeral TEST keys, then reject substituted artifacts, tree/run/job/challenges, wrong runner/signer, wrong public keys, expired/revoked keys, and forged signatures.

**Trust limitation:** `runner_identity` is inside the signed statement; cryptography alone does not verify that a runner was truly trusted. The independent signing authority must attest that property before signing. A signature over an unreviewed workflow claim is NOT guest certification.

### Offline private-signature byte-checking CLI

`cargo +1.88.0 run --locked --bin private_signature_verify -- PUBLIC_PEM SIG64 ARTIFACT_ZIP APPROVED_KEY_SHA256 KEY_ID VALID_FROM VALID_UNTIL false REPO HEAD TREE CASE_SHA256 RUN_ID ATTEMPT JOB_ID NONCE SIGNER_WORKFLOW RUNNER_ID BACKEND FEATURE` verifies a signature on a deterministic context statement that binds **the freshly hashed ZIP bytes** and every identity field. Inputs are bounded to 8 KiB PEM, 64-byte signature and 16 MiB ZIP, with `NOT_CERTIFIED` on all outputs, even positive signature verification. It exits 3 for a positive cryptographic check, 2 otherwise, never 0 for release certification.

**Important:** caller-supplied KEY_PIN_SHA256, key dates, revoked status, repository and runner fields are only as trustworthy as the external protected configuration providing them. A user can supply a self-generated key and sign arbitrary claims, so this CLI MUST NOT be used as an independent proof of actual execution or as a release gate without a separately authenticated policy, reviewed source and runner provenance. The production end-to-end `guest_artifact_probe` still requires its existing GitHub attestation and independent challenge gates; the new offline CLI does **not** bypass them or enable an alternate certification path.
